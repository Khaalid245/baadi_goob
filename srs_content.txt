PART A: REQUIREMENTS
1. INTRODUCTION & SCOPE
1.1 Purpose
Furan is a two-sided web platform connecting Somali college students and young talent with internships, jobs, and skill competitions, while giving businesses, startups, and government institutions an efficient way to discover and hire qualified entry-level talent. This document specifies the requirements for the Furan MVP.
1.2 Problem
Roughly 500,000 young Somalis enter the labour market every year, but only about 80,000 jobs are created annually (World Bank). Students lack a dedicated platform to showcase skills or find internships, and employers struggle to find qualified young talent. Existing platforms (SomaliJobs, Shaqo, FursadLink) are general job boards skewed toward NGO/international listings, not built around student profiles or employer-hosted competitions.
1.3 Scope
Included in MVP:
Student registration and skills/project profile
Businesses posting internships, jobs, and competitions
Students browsing and applying to opportunities
Businesses reviewing and shortlisting applicants
Basic competition/hackathon listing and registration
Excluded from MVP (future phases):
Payment processing (paid competitions, premium listings)
AI-based skill matching and recommendations
Native mobile applications (web-first for MVP)
In-app messaging between students and employers
1.4 Intended Users & Stakeholders
Students — primary users seeking opportunities
Businesses, organizations, and government bodies — posting and hiring
Founding/development team — building and maintaining the platform
Future investors or partners — secondary stakeholders

3.1 Alternative & Error Flows (selected)
If a student applies without a complete profile (e.g. missing skills), the system shall prompt them to complete the profile before submitting.
If a business attempts to post an opportunity before verification is complete, the system shall block the action and display a pending-verification message.
If an opportunity's deadline has passed, the system shall disable the Apply button and label the listing as Closed.
If a student tries to apply to the same opportunity again, the system shall block the action and show an "Already applied" message.
If a user opens a page or action that their role is not allowed to use, the system shall show an "Access denied" message.
If login fails, the system shall show a general error message that does not say whether the email or the password was wrong.
If a suspended user tries to log in, the system shall block login and show an account-suspended message.

7.2 Validation Rules
Email fields must follow a valid email format and be unique per account
An opportunity's deadline must be a future date at the time of posting
A student may not submit more than one application per opportunity (see FR-015)
A student may not register twice for the same competition
Competition registration is allowed only for opportunities of type competition
7.3 Data Relationships
A User has one Profile (Student or Business). A Business posts many Opportunities. A Student submits many Applications, each linked to one Opportunity. A Student can have many CompetitionRegistrations, each linked to one competition Opportunity.
7.4 Privacy, Storage & Retention
A student's personal data is only visible to a business after that student applies to its opportunity
Application data is retained for at least 12 months for reporting purposes. If a student deletes their account (FR-020), their personal details are removed and the application record is kept without personal details for the rest of the 12 months
Database is backed up daily and retained for 30 days (see NFR-10)
8. USE CASES & WORKFLOWS
8.1 Use Case: Student Applies to an Opportunity
Actor: Student
Precondition: Student is registered and has a complete profile
Main flow:
Student browses or searches opportunities.
Student selects an opportunity and views details.
Student clicks Apply.
System submits the application using the saved profile.
System confirms submission and updates status to New.
Alternative flow: If the profile is incomplete, system prompts the student to complete it before applying (see FR-004).
Error scenario: If the opportunity deadline has passed, the Apply button is disabled (see Section 3.1).
Expected result: An Application record is created and visible to both student and business.
8.2 Use Case: Business Posts an Opportunity and Reviews Applicants
Actor: Business
Precondition: Business account has been verified by an administrator
Main flow:
Business selects "Post opportunity".
Business enters type, title, required skills, and deadline.
System publishes the listing.
Students apply over time.
Business views the applicant list and reviews profiles.
Business updates applicant status (Shortlisted/Rejected/Hired).
Alternative flow: Business edits or closes the listing before the deadline.
Error scenario: If the business is not yet verified, posting is blocked with a pending-verification message (see Section 3.1).
Expected result: Opportunity is visible to students; applicant statuses are tracked and visible to the business.
8.3 Use Case: Administrator Verifies a Business
Actor: Administrator
Precondition: A business has registered and its status is pending
Main flow:
Administrator opens the Verify businesses page.
System shows the list of pending businesses.
Administrator opens one business and checks its details.
Administrator selects Verify or Reject.
System saves the decision and notifies the business (FR-019).
Alternative flow: Administrator rejects the business; it cannot post opportunities.
Expected result: A verified business can post opportunities (see Business rules, Section 10).
8.4 Use Case: Student Registers for a Competition
Actor: Student
Precondition: Student is logged in; the competition is open
Main flow:
Student opens the Competitions list and selects a competition.
Student clicks Register.
System saves the registration.
System confirms and shows the competition in the student's dashboard.
Error scenario: If the deadline has passed or the student is already registered, the system blocks the action and shows a message.
Expected result: A CompetitionRegistration record is created and visible to the business that posted the competition (FR-018).
9. REQUIREMENT QUALITY
Each requirement in this document is written to be clear, specific, unambiguous, complete, consistent, testable, feasible, traceable, and necessary. Requirements use the defined ID scheme (FR-xxx, NFR-xx) so they can be traced to use cases and, later, to test cases.
10. BUSINESS RULES
Approval rule: A business account must be verified by an administrator before it may post opportunities.
Eligibility rule: Only registered students with a complete profile may apply to opportunities.
Validation rule: An opportunity may not be posted with a deadline in the past.
Restriction: A student may submit only one application per opportunity.
Time limit: Applications are not accepted after an opportunity's stated deadline.
Role-based rule: A business may only view and manage applicants for its own postings.
Suspension rule: A suspended user cannot log in until an administrator reactivates the account.

B3.2 Backend rules
Use Node.js current LTS and TypeScript with strict mode on.
Organise code by feature modules: auth, users, profiles, opportunities, applications, registrations, admin, notifications. Inside each module use routes, controllers, services, and data access (NFR-08).
Add one role-check middleware (student, business, admin) that enforces the permissions table in Section 5.
Validate every request body and return the standard error codes listed in B4.
Add security basics: helmet, CORS limited to the frontend domain, and rate limits on login and password reset.
Add a GET /health endpoint. The uptime monitor and the deploy pipeline use it.
B3.3 Frontend rules
Use React with TypeScript strict mode, built with Vite.
Load each page lazily (code splitting) to stay under the 1 MB first-load target.
Design for screens from 360 px wide (NFR-11). Test on a real phone.
Use the OpenAPI file to type the API calls, so a backend change shows up as a compile error.
Read the API address from an environment variable, not from code.
B3.4 Database rules (MySQL)
Use MySQL 8, InnoDB engine, and utf8mb4 character set (needed for Somali and Arabic names).
Create the tables from Section 7 with foreign keys. MySQL has no array type, so store skills[] and project_links[] as JSON columns (or as child tables if skill search becomes slow).
Add unique indexes: User.email, Application (student_id, opportunity_id) for FR-015, and CompetitionRegistration (student_id, opportunity_id).
Add an index on Opportunity (type, status, deadline) for filters (FR-003) and a FULLTEXT index on title and description for keyword search (FR-023).
Change the schema only through migration files in the repository. Nobody edits the production database by hand.
Back up the database every day and keep each backup for 30 days (NFR-10). Store a copy outside the server. Test one restore before launch (NFR-04).
B3.5 Production DevOps
The goal is simple: every change is tested automatically, tried on staging, and then released to production in the same way every time.
Environment
Purpose
How it is updated
Local
Developers work here. Docker Compose runs frontend, backend, and MySQL with one command
Developer runs it
Staging
Same setup as production with test data. Every feature is checked here
Deploys automatically when a pull request is merged to main
Production
Real users and real data
Deploys after a team member approves, from a version tag (for example v1.0.0)


Source control: GitHub with one repository and two folders, /backend and /frontend. Branch rules are in B7.
CI (GitHub Actions): on every pull request, install, lint, type-check, run tests, and build. A pull request cannot be merged if any step fails. Also run npm audit to catch unsafe packages.
CD (GitHub Actions): build Docker images, push them to GitHub Container Registry, and deploy to staging, then to production after approval. To roll back, redeploy the previous image.
Containers: the backend runs as a Docker container. The frontend is built into static files and served by Nginx.
Server: a Linux server (Ubuntu LTS) or cloud VM running Docker Compose, with Nginx as the entry point. Nginx serves the frontend and sends /api requests to the backend.
HTTPS: free certificates from Let's Encrypt, renewed automatically (NFR-01). Optional: Cloudflare in front for caching and extra speed.
MySQL in production: a provider-managed MySQL if the budget allows. Otherwise a MySQL container on a persistent volume, with the daily backup from B3.4.
Configuration and secrets: use environment variables. Never commit a .env file. Keep secrets in GitHub Actions secrets and on the server. Use different values for staging and production.
Logs and monitoring: structured JSON logs from the backend, an uptime monitor on /health that alerts the team by email or phone (NFR-13), and optional error tracking such as Sentry.
Server security: firewall allows only ports 80, 443, and SSH. SSH keys only, no password login. Update the operating system and packages regularly.
First admin account: created by a seed script on the server, never by public registration.

B7. WORKING RULES
Keep two folders in one repository: /backend and /frontend
Do not commit directly to main. Use a branch for each feature, named with the requirement ID (example: feature/FR-004-apply)
Put the requirement ID in each pull request title
Every pull request needs one review from another team member
A pull request can be merged only when CI passes (lint, type-check, tests, build)
A feature is done when: it works as the FR says, it has a test, it was reviewed, the API docs are updated, and it works on a phone-size screen
